# Feature-to-Table Matrix

**Scope:** `MOODLE_SUBSET_V1`

**Selection size:** 13 CORE + 7 SUPPORTING = 20 tables

**Physical-schema evidence:** `TEACHER_SCHEMA_REFERENCE`

Ma trận này giải thích vì sao từng bảng được chọn và dữ liệu nào được dùng cho từng chức năng. Đây là bản đồ phân tích/fixture, không phải kế hoạch cho Flutter truy cập database. Mọi thao tác production phải đi qua HTTPS và Moodle application/API layer đã được DLU phê duyệt.

## Coverage ledger

Mỗi bảng trong subset cố định được dùng bởi ít nhất một feature:

- CORE (13): `user`, `course`, `enrol`, `user_enrolments`, `course_sections`, `modules`, `course_modules`, `resource`, `assign`, `assign_submission`, `assign_grades`, `grade_items`, `grade_grades`.
- SUPPORTING (7): `course_categories`, `files`, `context`, `role`, `role_assignments`, `course_modules_completion`, `event`.

## Evidence and feature boundaries

- Login không được thực hiện bằng cách đọc bảng `user`; production authentication phải dùng Moodle Web Service hoặc phương thức application-layer được DLU xác nhận.
- Resource delivery không được mở trực tiếp Moodle file pool; API/file endpoint phải authorize từng request.
- Role tables chỉ hỗ trợ presentation, không cho phép client tính authoritative permissions. Server phải kiểm tra capability trong context tương ứng.
- `assign_submission` chỉ chứa submission metadata; nội dung thực nằm trong assignment plugins theo reference và nằm ngoài V1.
- Việc có bảng trong schema không chứng minh DLU đã expose Moodle API function tương ứng. Schema coverage và API availability là hai gate riêng.
- Fixture deterministic có thể cover mọi UI state nêu trên nhưng luôn là `SYNTHETIC_DATA`, không phải `DLU_LIVE_EVIDENCE`.
